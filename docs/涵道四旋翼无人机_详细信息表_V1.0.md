## 3. 机体几何、外参与 TF

### 3.1 机体包络

采用FLU约定：X向前、Y向左、Z向上。单位为米。

| 轴 | 最小值 | 最大值 |
|---|---:|---:|
| X | -0.30 | +0.30 |
| Y | -0.35 | +0.35 |
| Z | -0.10 | +0.10 |

八个顶点统一保存在 `src/ducted_bringup/config/airframe_geometry.yaml`，由地面高度和局部避障启动文件共同加载。
避障算法采用包住该长方体的球体，半径约0.4717 m，再加入净空及运动余量；此半径是算法包络，不是机体实际半宽。

### 3.2 两类外参

| 配置关系 | 平移，m | 旋转 | 使用位置 |
|---|---|---|---|
| MID360内部雷达到内部IMU | `[-0.011, -0.02329, 0.04412]` | 单位矩阵 | 建图、重定位的 `mapping/extrinsic_T`、`extrinsic_R` |
| 内部IMU状态坐标系在 `base_link` 中的安装位姿 | `[0.13, 0, 0]` | RPY=`[0.03, 0.4567, 0]` rad | 里程计适配器的 `extrinsic/base_to_livox` |

安装角约为Roll 1.72°、Pitch 26.17°、Yaw 0°。配置复用本机原厂 `spirit-wing_v1.0` 的MID360启动文件；其中静态TF命令的角度顺序为yaw、pitch、roll，转换到YAML后采用roll、pitch、yaw。

`reused_unverified` 表示这份原厂安装配置没有在本轮独立测量精度，不表示来自其他机型。
FAST-LIO的 `body` 状态（原命名为`livox_frame`）位于MID360内部IMU原点；内部雷达—IMU外参不能再作为机体安装平移重复叠加。

### 3.3 TF发布关系

适配器有效工作时，定位主链为：

~~~text
odom → camera_init → body → base_link
~~~

| TF | 行为 | 发布者 |
|---|---|---|
| `odom → camera_init` | 初始化后固定旋转，随有效里程计时间戳发布 | `/localization_frames`（`fastlio_odometry_adapter.py`） |
| `camera_init → body` | FAST-LIO动态状态 | 建图`/mapping`；重定位`/ducted/local_lio/fastlio` |
| `body → base_link` | 安装关系的逆变换，作为静态TF发布 | `/localization_frames`（`fastlio_odometry_adapter.py`） |
| `odom → odom_ned` | ENU/NED坐标约定转换 | MAVROS内部话题（不进入公共TF树） |
| `base_link → base_link_frd` | FLU/FRD坐标约定转换 | MAVROS内部话题（不进入公共TF树） |

MAVROS的 `local_position/tf/send=false`，不再发布另一条 `odom → base_link` 动态边。
基础层单独运行时不会提供完整定位主链。建图或重定位自动启动 `/localization_frames`，在定位有效且未解锁飞控姿态可用后连接完整TF；外部发送门控关闭不影响TF。

## 4. 正式启动入口

所有入口均属于 `ducted_bringup`。先启动基础层，再按需启动其他功能。

| 功能 | 命令或入口 | 默认行为 |
|---|---|---|
| 基础层 | `roslaunch ducted_bringup base_system.launch` | MAVROS、Livox、健康监视 |
| 建图 | `roslaunch ducted_bringup mapping.launch` | 等待基础层；显式保存地图 |
| 重定位 | `roslaunch ducted_bringup relocalization.launch map_file:=/绝对路径/GlobalMap.pcd` | 加载指定PCD，输出匹配就绪状态 |
| 外部里程计 | `external_odometry.launch` | `input_contract_confirmed=false` |
| 相对地面高度 | `terrain_height.launch` | `reference_confirmed=false` |
| 遥控处理 | `rc_processing.launch` | `mapping_confirmed=false` |
| 飞控执行器 | `flight_control.launch` | `enable_flight_output=false`，自带一份RC监视 |
| 全局＋局部规划 | `global_local_planning.launch`；需要占据数据文件 | `geometry_confirmed=false`、`enable_output=false` |
| 航点任务 | `waypoint_mission.launch` | `enable_commands=false`，启动不执行任务 |
| 数据记录 | `recording.launch` | 基础层连续就绪后建立记录 |
| 按需组合 | `modules.launch` | 所有功能开关默认关闭，不隐式启动基础层 |

建图与重定位不能同时运行。组合入口同时选择飞控和RC处理时只启动一份RC监视。

## 12. 故障矩阵

| 现象 | 诊断顺序 |
|---|---|
| SSH不通 | 主机供电 → `192.168.50.140` → WLAN → 路由 |
| 无雷达数据 | eth0地址 → `192.168.1.109` → JSON主机IP → 驱动 → 点云/IMU |

| FAST-LIO无输出 | 基础就绪 → 点云/IMU → 初始化 → 对应分支参数 |
| 重定位不就绪 | PCD路径 → 场景对应关系 → 初始位姿话题 → 匹配日志 |
| 外部里程计无输出 | 确认门控 → 基础/重定位就绪 → 锁定FCU姿态 → frame → 时间戳 |
| AGL无效 | 参考门控 → 精确时刻TF → 点云/位姿同步 → 地面支撑 → 台阶歧义 |
| RC无效或闭锁 | 映射门控 → 原始PWM → 急停 → 数据源年龄 |
| 避障阻挡/停止输出 | 三维包络 → 地形有效性 → 障碍/制动范围 → 控制状态 → 无进展原因 |

| 保存地图失败 | 建图节点仍在运行 → 目标目录尚不存在且父目录可写 → `success` → 七个文件大小 |

后台保存入口：`rosrun ducted_bringup save_map.py start --destination /新地图目录`；查询使用`rosrun ducted_bringup save_map.py status`。提交后必须等待`SUCCEEDED`再关闭建图。任务文件位于`logs/map-save-jobs/`；逐帧进度参数为`/ducted/mapping/save_progress`。


本版按运行阶段划分公共TF（2026-09-11更新）：

- 仅基础系统：无定位TF边，不出现`map`、`odom`、`camera_init`或`body`定位链；`base_link`为机体参考。
- 建图：`odom → camera_init → body → base_link`，不存在`map`。
- 重定位成功且源数据新鲜：`map → odom → camera_init → body → base_link`。

`camera_init → body`由独立的局部FAST-LIO发布。重定位时额外运行局部scan-to-map里程计；原`sfast_lio`负责地图匹配，只发布`/ducted/relocalization/global_odom`（map/body）且不发布TF。`world_tf_owner.py`按相同扫描时间戳配对全局与局部机体位姿，计算`T_map_odom = T_map_base × inverse(T_odom_base)`；全局校正不会重置局部FAST-LIO。数据过期或重定位无效时停止发布全局校正，`/ducted/localization/map_ready=false`。TF缓存可能短暂保留旧变换，不应只看树中是否还显示map判断定位有效。

`body`是MID360内部IMU参考，不是机体中心；`body → base_link`为原安装外参的逆变换，外参数值未改。保存PCD坐标沿用建图的`camera_init`数值，加载后将该固定地图坐标命名为`map`，建图时无需发布map TF。重定位RViz的Fixed Frame使用`map`；建图使用`odom`或`camera_init`。

MAVROS的ENU/NED、FLU/FRD辅助变换移至`/mavros/internal_tf_static`，其内部里程计转换仍使用这些变换，公共TF树不再出现辅助根。旧`odom → map`链已移除。重定位阶段增加一个局部FAST-LIO进程，计算负载高于原单进程方案。
